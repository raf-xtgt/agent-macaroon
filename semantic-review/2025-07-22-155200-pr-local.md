# Live Model Armor tuning, defense profile export, and fleet defense panel wiring

This change adds runtime tuning of the Model Armor template via a new `POST /armor/tune` endpoint, exposes the current template configuration through `GET /armor/config`, and introduces a `GET /armor/export` endpoint that serializes the full defense posture (registry ceilings, tool maps, armor config, immunization patterns) as a downloadable JSON profile. On the frontend, a new `TuneDefensesPanel` component pre-populates form state from the live config and submits tuning changes; `FleetDefensePanel` gains an export-download button; and `live/page.tsx` wires both into the idle and active session layouts.

Watch for: The `/armor/tune` endpoint returns HTTP 200 with `success: false` for SDK failures, which the frontend handles but which breaks REST conventions and will confuse non-UI consumers (confirmed). The export endpoint walks `GatewayPlugin` private attributes (`_tool_action_map`, `_initial_scope`, etc.) via `hasattr`/`getattr`, creating a coupling that any refactor of attribute naming will silently break (confirmed). The `TuneRequest` Pydantic model types `rai_filters` as `list[dict[str, str]]` rather than a structured model, so typos in dict keys pass validation silently (confirmed).

## High-level view

The backend adds `get_template_config()` and `tune_template()` in `model_armor.py`. `tune_template()` builds a protobuf `Template` and calls `update_template` with a `FieldMask` covering `filter_config` and `template_metadata`. Both are fail-safe. The test verifies the exact mask paths and template resource name.

The API layer adds three routes: `/config` (pass-through), `/tune` (allowlist validation then delegate to `tune_template()`), and `/export` (aggregate registry, plugin, armor, and immunization data into a JSON snapshot). The export avoids secret material but reaches into private plugin attributes, and its secret-absence test is string-based rather than structural.

The frontend `TuneDefensesPanel` fetches `/armor/config` on mount and maps the response into per-field state hooks, POSTs the assembled config back to `/armor/tune`, and uses `fieldset`/`legend`, `aria-label`, and `aria-expanded` for accessibility. `FleetDefensePanel` gains a conditional export-download button.

The wiring in `live/page.tsx` extracts armor-status polling into a `useCallback` and passes it as `onTuneApplied` so the tuning panel can trigger an immediate re-poll after a successful update.

## `tune_template()` protobuf construction

The enforcement enum for PI/jailbreak uses a double-`getattr` chain to handle SDK version differences (`FilterEnforcement` vs `PiAndJailbreakFilterEnforcement`), with a final fallback to integer 1/2. This pattern is repeated for malicious URI and SDP enforcement. It's defensive but makes the code harder to maintain when the SDK stabilizes its enum names. A comment noting this is intentional SDK-version handling would help future readers.

The `getattr` fallback pattern for enum resolution (e.g., `getattr(ma.DetectionConfidenceLevel, pi_conf_str, ma.DetectionConfidenceLevel.LOW_AND_ABOVE)`) means an invalid confidence string silently falls back to the default rather than erroring. This is safe because the API layer validates strings before calling `tune_template()`, so the fallbacks only fire if the two layers drift — worth noting with a comment.

## Tune failure returns 200

When `tune_template()` catches an SDK exception and returns `{"success": false, "error": "..."}`, the API handler at line 110-115 of `api.py` returns this as a 200 response. The frontend handles this correctly — `TuneDefensesPanel.handleApply()` checks `res.ok && data.success` — but any non-UI consumer of `POST /armor/tune` will see 200 and need to inspect the body. Returning 502 for SDK errors would be more idiomatic.

## `TuneRequest` rai_filters schema gap

```python
class TuneRequest(BaseModel):
    rai_filters: list[dict[str, str]] = []
```

A payload like `[{"filter": "DANGEROUS", "level": "HIGH"}]` passes Pydantic validation. Then `.get("type")` returns `None`, which fails the allowlist check and returns 400 — not a security issue, but the error message reads `"Invalid rai_filter[0].type 'None'"`. A typed model gives a clearer rejection:

```python
class RaiFilterItem(BaseModel):
    type: str
    confidence_level: str

class TuneRequest(BaseModel):
    rai_filters: list[RaiFilterItem] = []
```

## Export endpoint private attribute coupling

```python
for plugin in getattr(governed_app, "plugins", []):
    if hasattr(plugin, "_tool_action_map"):
        tool_action_map = dict(sorted(plugin._tool_action_map.items()))
```

There is no type check — it reads from whichever plugin has the attribute. If `GatewayPlugin` renames `_tool_action_map`, the export silently returns an empty dict. The `test_get_armor_export_structure` test asserts keys exist and are correct types, but not that they contain actual fleet data — the test would pass even if the `except Exception` branch swallowed an import error and returned defaults.

The export does correctly avoid secret material. `GatewayPlugin._root_key` is never accessed — the code only reads attributes in its explicit `hasattr` list. The `test_get_armor_export_no_secrets` test confirms `"root_key"` does not appear in the response body.

## TuneDefensesPanel config pre-population

The RAI filter mapping initializes all four types as disabled, then enables only those present in the response array. Disabling a type in the UI removes it from `rai_filters` entirely rather than sending it with a "disabled" flag — this matches the backend semantics where absence of a filter type means disabled.

## Test coverage gaps

Not tested: `TuneDefensesPanel` has no unit tests (expected — no frontend test framework). The export endpoint test runs against the real governed app import path, which may or may not succeed depending on whether `target_fleet/` is symlinked — the `except Exception: pass` blocks mask import failures, so the test passes with default/empty values in CI environments without the symlink.
